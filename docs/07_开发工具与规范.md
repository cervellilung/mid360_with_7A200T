# FPGA、嵌入式与桌面开发规范

更新：2026-10-01。适用：现行 ACX750 两套工程、树莓派 5 服务和用户界面。后续开发先读本文件及《项目总交接》。本文件落实用户提供的全局 FPGA / AGENTS.md 指令，并结合本轮 Route Design 审计补充防复发要求；规则不能代替实际综合、时序和上板证据。

**完整 FPGA 设计是 RTL＋约束＋工具设置＋实现结果。** 功能仿真正确仅是其中一项。修改前先读顶层层级、实际实例、接口、已有代码约定、IP、XDC、时钟/复位及工具报告；不得凭文件名、局部代码或软件代码风格推断整个硬件。保留命名和协议，优先最小必要修改。

## 1. 三类开发不能套用同一种思路

| 项目 | FPGA RTL | 嵌入式 Linux／MCU | 桌面／树莓派服务／界面 |
|---|---|---|---|
| 程序本质 | 描述每拍同时存在的硬件、连线与存储端口 | CPU 顺序执行；并发来自任务、IRQ、DMA等 | CPU/GPU执行；并发来自线程、进程、事件循环等 |
| `for` | 常量循环通常展开并行硬件，必须预算实例、端口和扇出 | 顺序循环，预算执行时间与中断阻塞 | 顺序或向量运算，预算CPU/内存和响应时间 |
| 数组索引 | RAM端口或MUX/译码网络，取决于RTL模板 | 内存地址访问，关注缓存、越界与对齐 | 内存访问，关注复制、分配与算法复杂度 |
| 复位／初始化 | 复位引脚、控制集合、启动逐地址清理 | 启动初始化、状态恢复、设备复位 | 对象初始化、资源生命周期、错误恢复 |
| 接口 | 拍级握手、端口数量、CDC、时序 | 驱动API、DMA所有权、缓存一致性、超时 | 消息、网络、文件、异步API和背压 |
| 首要性能证据 | 实际网表、Slice装箱、扇出、拥塞、WNS/WHS、II | 真实帧率、IRQ/调度延迟、CPU、DMA与丢包 | P95/P99处理时间、队列年龄、渲染帧率、内存 |

树莓派服务器也是嵌入式部署环境，不能因为使用Python就忽略其有限内存、存储和CPU；桌面模拟吞吐不等于树莓派实机吞吐。

## 2. 写 FPGA 代码前先确定硬件结构

新增模块在编码前必须写清：时钟/频率、输入峰值、吞吐率/II、延迟预算、最大数据量、存储深度/位宽、每拍读写端口数、复位和有效性、时钟域、缓存所有权、溢出处理。

- 算法循环先选并行、部分并行或串行状态机，不能直接翻译软件双重循环。
- 内存先选存储原语和端口，再写数组。不能先写任意多读多写数组，最后指望 `ram_style` 自动修复。
- 结果列表、畸变表、遥测包通常按地址读或按记录流动；少量控制参数可并行广播。
- 视频像素链路保持一拍一个像素的稳态吞吐。元数据的串行化与像素的串行化必须分开评估。
- 算法对拍以整数参考输出为准；不要为缩位宽、共享运算或修时序偷偷更改舍入、饱和、边界和排序。

默认交付可综合 RTL，testbench 与 simulation-only 内容明确分开。SystemVerilog 时序用 `always_ff` / non-blocking `<=`，组合用 `always_comb` / blocking `=`；组合出口完整赋值，避免 latch 和组合环。每个时序块属于一个时钟域。参数化合理的宽度、深度和门限，不以压缩代码行数为优化目标。

## 3. 存储和接口怎么选

| 使用场景 | 优先方案 | 避免的结构／必须核对的例外 |
|---|---|---|
| 大结果快照、包缓存、查表 | 同步读BRAM/XPM；单写或真实双端口；请求/响应流水线 | 整片同时reset、任意多地址同拍写、所有元素并行输出 |
| 小异步读表、visited位图 | LUTRAM；明确单写端口；需要时分bank | 不是所有数组都必须BRAM；转换后增加的读延迟必须匹配 |
| 跨时钟FIFO | XPM/FIFO Generator；明确FWFT、深度、溢出及复位协调 | 手写Gray指针不是自动正确；不能仅把memory属性改block而不改读控制 |
| 少量每拍都要访问的参数 | 寄存器，按消费者分组 | 为“统一结构”将它们全部移入单口RAM会降低吞吐 |
| 静态ROM | 明确初始化与同步读模板；核对综合报告 | 综合可识别的initial ROM与运行时reset清零不是一回事 |
| 大型跨模块结果 | `data/valid/ready`或地址/响应接口；固定记录布局 | 数千位快照总线后接动态字节选择、重复全量复制 |
| CDC少量状态 | 单bit同步器；多bit用握手快照／异步FIFO | 多bit逐位双拍同步不能保证同一份结果 |

超过256bit的跨模块接口必须记录为何需要并行、消费者和更新率；超过1024bit必须先画出存储/读端口结构。这是审查触发值，不是禁止阈值。

## 4. FPGA RTL 的可用与慎用写法

### 可以使用，但必须知道综合成什么

- 小规模 `generate`、固定切片、常量循环：例如4条RGMII数据通道、5位BCD修正、8级短延迟线。
- 参数/常量计算中的 `/`、`%`、`*`：编译期运算不产生运行时除法器。
- 固定距离移位、Gray码 `b ^ (b >> 1)`：通常是接线和异或，不能误报成barrel shifter。
- 常量乘法：可能是移位加法或DSP，按实际综合结构决定。
- 变量索引：若对应合法RAM端口是合理结构；若对大寄存器列表异步读则可能是大型MUX。
- 像素同时检查多个框：为了维持一像素/拍可以并行；若插流水线，RGB、valid、SOF、EOL、坐标必须同步延迟。

### 不作为默认实现方式

- 时钟块中对大数组循环清零、同拍复制全部元素、同拍多个任意地址写入。
- 将一个memory展开为数千位接口，再以变量切片选一个字节。
- 在一拍内串联“大MUX→乘法→加法→比较→状态跳转”。
- 没有范围证明地使用32/64bit计数、乘法或宽signed扩展；也不能反向盲目缩位宽。
- 对所有datapath寄存器统一加reset；按每个字节创建不同CE/SR；组合译码输出跨大片区域广播。
- 靠全局 `DONT_TOUCH`、强制扇出约束或紧Pblock遮住结构问题。
- 为过时序添加没有功能依据的false_path/multicycle；或屏蔽DRC。

## 5. 复位、位宽、运算和低延迟

### 复位

复位保留在状态机、valid、FIFO指针、CDC握手、计数和安全状态。被valid严格屏蔽的RAM数据、乘法中间量、完整写入后才发布的payload，可以不复位，但必须证明任何消费者都不会读取尚未初始化的内容。

若协议要求复位后读零，使用逐地址初始化并在完成前拒绝访问，或按字/记录保存初始化有效标记；不能仅用整个bank一个valid就允许未写地址返回随机值。动态修改部分配置也必须保留其他字段，不能无条件切到未完整复制的新bank。

RAM读写过程独立于异步复位控制过程；需要初始化时用正常写端口顺序清理。各时钟域同步释放；不要删除安全控制复位来换资源。

### 时钟、CDC 与 RDC

为每个时钟域记录来源、频率、generated clock关系、复位及跨域接口。普通逻辑不生成或门控时钟，使用 BUFG/BUFGCE、MMCM 等专用资源；时钟切换同时明确停流、复位和恢复规则。只有证明时钟实际异步、路径符合CDC协议后，才配置对应时序例外。

| 跨域内容 | 默认方式 | 必须核对 |
|---|---|---|
| 单bit稳定level | 至少两级同步器，目标器件适用的 `ASYNC_REG` | 输入优先来自源域寄存器；复位释放和脉冲宽度 |
| 单次pulse/event | toggle或请求/应答握手 | 事件最小间隔、忙时处理、不能丢失/重复 |
| 多bit控制或低频结果 | 稳定快照握手 | 数据保持窗口、采样与ack、不能逐bit同步拼成错误结果 |
| 连续多bit流 | 异步FIFO | 时钟比、FWFT语义、满/空、两侧复位协调和溢出 |
| 跨域counter | Gray编码及合适同步/约束 | 不能假设任意二进制counter可直接采样；复核bus-skew |

CDC和RDC分别检查数据跨域与复位关系。保留同步器/握手/FIFO控制复位；数据复位删减必须证明有效性屏蔽与复位期间协议安全。

### 位宽和运算

- 写出合法范围及中间值上界，明确signed/unsigned、乘积位数、加法进位、截断和饱和。
- `integer/genvar`作为循环变量不一定产生32bit寄存器；存储为状态、计数或参与可变运算时才重点检查。
- 共享低频运算器时评估最坏任务数和处理周期，不能只看单次延迟。
- 流水线优先放在RAM读出、MUX结果、乘积、加法和比较结果的边界；先看路径逻辑/布线占比。
- 延迟按 `新增周期/f_clk` 报告，串行循环同时报告 `新增周期×最大次数/f_clk`。这些是周期预算，不是端到端实测。
- 不增加整帧排队或多扫描周期等待。视频保留最新完整帧；数据录制的有界队列和展示的最新帧策略分别处理。

## 6. 嵌入式与桌面端具体规则

### 嵌入式 Linux／MCU

- 设备采集、网络发送、存储和UI分离；IRQ/回调不做大块编码、写磁盘或阻塞网络。
- 使用有界环形缓冲，明确DMA提交/完成/用户态读取/归还四个阶段。缓存一致性由匹配内核的DMA API处理，不复用裸机固定DDR地址。
- 超时、启动宽限、断流、重连、溢出、磁盘不足必须有状态和计数；MID-360保留12秒启动宽限。
- 低延迟展示优先最新完整帧；录制丢弃必须明确记录，不以“画面正常”证明无丢包。
- 重建/配准/表面网格在树莓派5服务端执行，按实际负载降更新频率；不将重CPU软件循环机械移入PL。
- MCU/裸机遵循实际CPU、RAM、栈与实时预算：避免在IRQ里动态分配或长时间阻塞；大缓冲先做容量证明，驱动并发用该平台适用的临界区/原子机制，`volatile`不是同步和缓存一致性方案。Linux侧采用内核提供的驱动、DMA和线程机制，不能照搬裸机固定地址与无限轮询。

### 桌面／网页

- UI线程只展示和交互，采集、解析、网格构建放后台；渲染资源复用，队列有界。
- 控制消息与视频数据分开，防止视频积压拖慢控制；序号、数据年龄和连接状态可见。
- 模拟、回放、真实设备使用同一协议/算法入口，但分别标注验证范围。
- 优化以采样耗时、内存、帧率和队列延迟为证据；源码短、使用向量化或多线程都不是性能保证。

## 7. 以后每次 FPGA 修改的检查流程

| 阶段 | 必须输出 | 何时不能进入下一阶段 |
|---|---|---|
| 设计评审 | 存储/端口/接口图、范围与延迟预算 | 大数组、多端口、宽总线和复位策略未确定 |
| 语法/展开、lint、小模块仿真 | 独立整数预期、边界、随机背压、初始化、溢出、reset、CRC/快照一致性 | latch、多驱动、组合环、功能或周期/吞吐预算失败 |
| CDC/RDC及适用的formal | 时钟/复位域表、跨域协议、稳定性/所有权/握手属性 | 无保护跨域、复位恢复错误、未解释的关键告警；formal按模块适用性采用 |
| 模块综合/OOC | 预期与实际RAM/DSP/FF、关键路径、推断警告 | 应进RAM的存储被溶成FF且无合理解释 |
| 整机综合预检查 | 层级LUT/FF/BRAM/DSP、control sets、高扇出、宽MUX与时序覆盖 | Error/未解释Critical Warning、资源/端口预算失败、严重逻辑超时未解释；布局前估算负裕量需分清逻辑与估算连线，不机械等同最终失败 |
| 布局检查 | Slice占用、空FF位置、拥塞、最差路径逻辑/布线比例 | 结构性拥塞未处理、严重逻辑超时；不能无限尝试策略 |
| 路由验收 | WNS/WHS≥0、DRC、CDC、bus-skew、外设时序覆盖 | 无完整路由报告、负裕量或关键DRC；不得称可上板bit |
| 上板 | 真设备、长时间吞吐、丢包、延迟、恢复 | 软件/仿真结果不能冒充板上完成 |

新增高扇出普通控制/数据网超过500负载时必须审查，超过2000优先解释结构；这些是本项目review触发值，不是Xilinx硬件限制。总Slice超过80%或明显高于LUT/FF占比时先查装箱和局部拥塞，不只加线程。

实际报告优先查看 `report_utilization`、`report_timing_summary`、`report_design_analysis -congestion`、`report_high_fanout_nets`、`report_control_sets`、`report_clock_interaction`、`report_cdc`、`report_methodology`、route status及实现日志；适用时补RDC、bus-skew和I/O时序。记录checkpoint阶段，不能把布局估算、路由中途和最终路由数值混为一谈。

问题先分类为功能、时序、CDC/RDC、综合/资源、布局布线、约束、仿真或硬件集成。每项修改写出文件/行号、硬件结构、资源与时序影响、具体流水线位置及latency/throughput；不能以“代码更漂亮”或单看LUT减少代替结构分析。允许少量额外LUT换取较少control sets、更好FF packing和routing，效果以同配置报告为准。

修改一次结构后进行同配置A/B比较：资源、control sets、扇出、最长MUX级数、Slice占用、拥塞、各阶段墙钟时间、最终WNS/WHS。只在结构合理后尝试实现策略/物理优化。综合/实现依次运行，线程参数沿用用户要求的16；工具内部阶段线程上限以日志为准。

运行过程统一使用编译监视器；人工停止标记为人工停止，保留日志/DCP，不写成自然失败。重置run之前归档已有报告。每个连续调查超过15分钟的问题，记录现象、假设、试错、排除项、剩余方向到 `LONG_RUNNING_ISSUES.md`。

# GLM-5.3-Flash 子任务执行器

该工具把明确、低风险的只读分析任务发送到 Z.AI Chat Completions API。GLM 只返回草案；Codex 主对话负责审核、修改文件、执行测试和验收。

## 调用

在项目根目录运行：

```powershell
.\run_glm_delegate.ps1 `
  --task "读取项目交接/状态文档，生成下一步 PC 红青 AR 仿真和固定点测试向量的 TODO 草案。" `
  --context PROJECT_STATUS.md `
  --context AI_HANDOFF.md
```

系统环境变量为 `ZAI_API_KEY`、`ZAI_BASE_URL` 和 `GLM_MODEL`。脚本只检查它们是否存在，不打印或保存密钥。

结果写入 `results/delegations/<UTC时间>_<任务名>/`：

- `result.md`：模型草案，固定包含“依据、TODO、验收条件、待确认项”。
- `metadata.json`：模型、上下文相对路径与摘要、耗时、token 用量和完成状态。

加 `--dry-run` 可只检查配置和上下文，不联网。上下文必须位于项目目录内、为允许的 UTF-8 文本，每个文件不超过 64 KiB，总量不超过 128 KiB。

## 安全边界

- 模型没有文件工具，不能修改项目。
- 脚本不执行模型输出中的命令或补丁。
- 不跟随 HTTP 重定向，防止认证头发送到其他地址。
- 任务和上下文若包含当前 API key、私钥或常见凭据格式，请求会被拒绝。
- 输出目录默认不纳入版本控制。结果仍须由 Codex 结合源代码、测试和硬件报告审核。

## 快速失败与缓存规则（2026-10-01）

- 先调用 build_750.tcl 的 preflight 模式，只综合并报告 setup 关键路径。建立时间 WNS<0 或 Critical Warning>0 时停在综合，不进入布局布线；预布线 hold 可能由布线修复，不在此门限中误判。
- 完成且 NEEDS_REFRESH=false 的综合结果复用；修改 RTL 或约束后自动重新综合。没有变化的 IP 不主动 reset。
- 布局后 WNS<-0.5 ns 时检查第一条最差路径：只有布线占比至少70%且WNS不低于-1.5 ns才允许尝试物理优化/路由；否则保存checkpoint后停止。报告无法解析时停止。该判断是构建早停策略，不改变最终路由时序要求。
- 布线已达标时跳过路由后优化；明显不达标时直接返回关键路径，避免无效重试；小幅负裕量才尝试 Explore。
- gate 模式直接复用路由结果，不重复打开综合。完整 CDC 报告改为时序通过后生成摘要；最终 bit 仍要求路由后 setup/hold 非负及 DRC 无 Error/Critical Warning。
- 上轮测得综合约5分钟、实现约34分钟、路由后优化约4分钟。不能保证完整合格镜像几分钟生成；目的是让明显失败提早暴露。

# 通用编译监视器

## 使用规则

今后执行本项目的编译、仿真、综合、布局布线及其他构建，统一通过 `tools/run_build.py` 启动。入口自动打开或复用 `user_app/build_monitor.py` 图形窗口，不再直接启动编译器而遗漏监视窗口。该入口接受任意编译命令和工作目录，不限定 ACX750 两个工程。

窗口可以同时记录不同任务，以页签切换。关闭窗口不停止后台编译；下次构建会重新打开。任务日志、退出码和历史时间存放在 `vivado_project/logs`，不默认上传。

窗口只显示所有正在运行的任务和最近三次已结束任务（包括失败任务），旧标签页自动移除；历史任务 JSON、日志与资源快照不删除。

手动打开：双击项目根目录的 `open_build_monitor.bat`。无需启动编译，已有窗口会复用并尝试恢复到前台；从其他工作目录运行也可以。依赖项目现有 `.venv`，不下载或安装软件。入口为 `tools/open_build_monitor.py`。

## 命令模板

从项目根目录运行：

```powershell
# 任意普通构建、C/C++ 编译或测试
.\.venv\Scripts\python.exe .\tools\run_build.py --name demo --kind build --cwd C:\your_project -- compiler.exe arguments

# Vivado 工程；--project 用于识别真实 run 阶段标记
.\.venv\Scripts\python.exe .\tools\run_build.py --name acx750_full --kind vivado --project .\vivado_project\acx750_full\acx750_full.xpr --cwd .\vivado_project\logs -- C:\Xilinx\Vivado\2020.2\bin\vivado.bat -mode batch -source C:/Users/ASUS/Desktop/FPGA/mid360_pc_fpga/tools/scripts/build_750.tcl -tclargs acx750_full
```

`--kind` 支持 `vivado`、`simulation`、`synthesis`、`build`。`--log` 可指定日志位置；`--estimate` 指定普通构建的初始估算秒数。编译器退出码会原样返回，失败不会被包装为成功。

## 进度含义

- Vivado 各阶段状态来自 `.runs` 的真实开始/结束标记及构建脚本的阶段事件。
- 无阶段标记的工具按一项构建显示实际运行状态。
- 总百分比与预计剩余时间是估算，不伪装成 Vivado 官方进度。首次估算使用初始时间，后续用本机历史耗时校准；运行中最多显示 99%，成功退出才显示 100%。
- 若编译器明确输出 `PROGRESS:N`，可读取它提供的进度；普通 Vivado 日志不会被假定有这种数据。
- 当前通用入口的成功退出、非零退出码、GUI 复用已检查。显示窗口不代表硬件功能验证。

## 实现文件

- `tools/run_build.py`：执行、自动打开窗口、输出日志、登记任务及退出码。
- `user_app/build_monitor.py`：只读显示、任务页签、阶段状态和预计时间。
- `tools/scripts/build_750.tcl`：两个新工程的综合、实现、路由后优化及 bit 门限。

构建默认依次进行，`launch_runs -jobs 16`，Vivado `general.maxThreads=16`。

## 阶段资源与失败诊断（2026-10-01）

- 每个阶段结束后显示 LUT、FF、BRAM、DSP 数量和可用时的占用比例。综合、布局、布线及优化阶段从 Vivado 实际资源报告读取，不通过日志猜测。
- 未单独生成报告时注明“沿用上次报告”；仿真没有实现资源用量，显示未生成报告。早于当前构建的旧报告不当作本轮结果。
- 新 Vivado 构建在实现优化、布局、布局后优化、布线后通过 `tools/scripts/hooks` 写入资源快照；已有正在执行的构建不打断，读取已生成报告。
- 失败时窗口显示退出码、最多 8 条去重关键报错、日志路径。Vivado 子运行日志也参与诊断；没有 ERROR 行时显示末尾线索，不编造错误原因。
- 显示程序可单独重启，不会终止编译进程。
- 实际综合/布局报告解析、错误去重和旧报告排除已离线检查通过。资源利用率不代表时序或实板验证通过。
